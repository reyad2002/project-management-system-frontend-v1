# API Contract — Project Files, Recurring Revenue/Expenses, Investments

> ⚠️ **متجاوَز (superseded)**: الباك إند الحقيقي اتبنى بعد كتابة الملف ده بشكل مختلف في تفاصيل مهمة (مثلاً: files بيتخزن كـ link مش رفع فعلي، أسماء حقول زي `linked_project_id`/`next_due_date` بدل اللي هنا، قيم enum مختلفة للـ types/status، `investments` من غير `total_returns` مباشر — فيه `/api/investments/summary` منفصل). الفرونت إند اتعدّل بالكامل ليطابق الباك إند الفعلي (راجع الكود في `lib/api.ts`/`lib/portal-api.ts` كمرجع دلوقتي). سايب الملف ده كسجل تاريخي بس — متبنيش حاجة جديدة عليه.

هذا الملف بيوثّق الـ contract اللي **الفرونت إند اتبنى عليه فعليًا** للفيتشرز دي، لأنه وقت الكتابة (2026-09-14) مفيش ولا migration ولا endpoint حقيقي ليها على الباك إند أو قاعدة الـ Supabase — تم التأكد من الاتنين. الفرونت إند اتصمم بافتراض الـ contract ده، فلو حد هيبني الباك إند الفعلي لازم يتبع نفس الأسماء والشكل هنا (أو يعدّل الفرونت إند لو اتغيّر حاجة).

نفس كونفنشنز الباك إند الحالي: `bigint` IDs (مش uuid)، `snake_case`، `company_id` على كل جدول، جدول `company` (مفرد)، أخطاء بشكل `{ error: message }`، الردود بصيغة JSON عادية.

## 1. Project Files

### DB (اقتراح)
```sql
create table project_files (
  id                bigint generated by default as identity primary key,
  company_id        bigint not null references company(id) on delete cascade,
  project_id        bigint not null references projects(id) on delete cascade,
  uploaded_by_type  varchar(20) not null check (uploaded_by_type in ('team_member','client_portal_user')),
  uploaded_by_id    bigint not null,
  category          varchar(20) not null check (category in ('deliverable','client_upload')),
  file_name         varchar(255) not null,
  description       text,
  file_url          text not null,
  mime_type         varchar(100),
  file_size         bigint,
  status            varchar(20) not null default 'pending'
    check (status in ('pending','approved','changes_requested')),
  review_note       text,
  created_at        timestamptz not null default now()
);

create table file_comments (
  id              bigint generated by default as identity primary key,
  file_id         bigint not null references project_files(id) on delete cascade,
  commenter_type  varchar(20) not null check (commenter_type in ('team_member','client_portal_user')),
  commenter_id    bigint not null,
  content         text not null,
  created_at      timestamptz not null default now()
);
```
`status`/`review_note` عندهم معنى فعلي بس لـ `category = 'deliverable'` (ملفات الفريق اللي محتاجة اعتماد العميل). ملفات `client_upload` بتفضل `status='pending'` افتراضيًا من غير أي workflow اعتماد عليها.

### Endpoints (Dashboard)
```
POST   /api/projects/:id/files            multipart/form-data: file, file_name?, description?
                                           (category دايمًا 'deliverable' من الداشبورد)
GET    /api/projects/:id/files            ?category=deliverable|client_upload
PATCH  /api/files/:id/status              body: { status: 'approved'|'changes_requested', review_note? }
                                           (مسموح من الداشبورد لو حابب الفريق يراجع حالة الملف بنفسه، لكن الاستخدام الأساسي متوقع من البورتال)
GET    /api/files/:id/comments
POST   /api/files/:id/comments            body: { content }
```

### Endpoints (Portal)
```
GET    /api/portal/projects/:id/files     ?category=
POST   /api/portal/files                  multipart/form-data: project_id, file, file_name?, description?
                                           (category دايمًا 'client_upload' من البورتال)
PATCH  /api/portal/files/:id/status       body: { status: 'approved'|'changes_requested', review_note? }
                                           (بس على ملفات category='deliverable' تابعة لمشروع العميل)
GET    /api/portal/files/:id/comments
POST   /api/portal/files/:id/comments     body: { content }
```

**إشعارات:** رفع deliverable جديد → إشعار لكل مستخدمي بوابة العميل (`file_uploaded`). تغيير status من العميل → إشعار لصاحب الرفع الأصلي بالفريق (`file_status_changed`). تعليق جديد → إشعار للطرف التاني (`file_comment_added`). رفع العميل لملف (`client_upload`) → إشعار للفريق (نفس نوع `file_uploaded` بس recipient مختلف، أو نوع منفصل لو حابب تفرّق في العرض).

## 2. Recurring Revenue (Hosting/Subscriptions من العملاء)

### DB
```sql
create table recurring_revenue (
  id                  bigint generated by default as identity primary key,
  company_id          bigint not null references company(id) on delete cascade,
  client_id           bigint not null references clients(id) on delete cascade,
  project_id          bigint references projects(id) on delete set null,
  type                varchar(20) not null check (type in ('hosting','domain','maintenance','subscription','other')),
  amount              numeric(12,2) not null,
  billing_cycle       varchar(10) not null check (billing_cycle in ('monthly','quarterly','yearly')),
  next_renewal_date   date not null,
  status              varchar(10) not null default 'active' check (status in ('active','cancelled')),
  notes               text,
  created_by          bigint not null references users(id),
  created_at          timestamptz not null default now()
);
```
`status` المخزّن بس `active`/`cancelled` — قيمة `overdue` **محسوبة** في الـ response (active + `next_renewal_date < today`) مش عمود منفصل، بنفس منطق `overdue` في الفواتير الحالي.

### Endpoints
```
GET    /api/recurring-revenue                ?status=active|overdue|cancelled&client_id=&project_id=
POST   /api/recurring-revenue                { client_id, project_id?, type, amount, billing_cycle, next_renewal_date, notes? }
PUT    /api/recurring-revenue/:id
DELETE /api/recurring-revenue/:id
GET    /api/recurring-revenue/upcoming       ?days=30   → أقرب استحقاقات (active بس) خلال N يوم
POST   /api/recurring-revenue/:id/mark-paid  → يدفع next_renewal_date قدام دورة واحدة حسب billing_cycle، status يرجع active
```

### Finance summary
```
GET /api/finance/hosting-summary
Response:
{
  "upcoming30DaysTotal": number, "upcoming30DaysCount": number,
  "overdueTotal": number, "overdueCount": number,
  "upcoming": [
    { "id", "client_name", "project_title": string|null, "amount", "next_renewal_date", "type" }
    // أقرب 5 بس
  ]
}
```

## 3. Recurring Expenses (اشتراكات سيرفرات/AI بتدفعها الشركة)

### DB
```sql
create table recurring_expenses (
  id                  bigint generated by default as identity primary key,
  company_id          bigint not null references company(id) on delete cascade,
  service_name        varchar(150) not null,     -- "AWS", "OpenAI", "Vercel Pro"...
  project_id          bigint references projects(id) on delete set null,   -- لو مرتبط بمشروع معين
  type                varchar(20) not null check (type in ('server','ai_tool','software','other')),
  amount              numeric(12,2) not null,
  billing_cycle       varchar(10) not null check (billing_cycle in ('monthly','quarterly','yearly')),
  next_renewal_date   date not null,
  status              varchar(10) not null default 'active' check (status in ('active','cancelled')),
  notes               text,
  created_by          bigint not null references users(id),
  created_at          timestamptz not null default now()
);
```
نفس منطق `overdue` المحسوب زي recurring_revenue.

### Endpoints
```
GET/POST      /api/recurring-expenses
PUT/DELETE    /api/recurring-expenses/:id
GET           /api/recurring-expenses/upcoming   ?days=30
POST          /api/recurring-expenses/:id/mark-paid
```

### Finance comparison
```
GET /api/finance/subscriptions-summary
Response:
{
  "revenue": { "upcoming30DaysTotal": number, "overdueTotal": number },
  "expenses": { "upcoming30DaysTotal": number, "overdueTotal": number },
  "netProjected30Days": number   // revenue.upcoming30DaysTotal - expenses.upcoming30DaysTotal
}
```

## 4. Investments

### DB
```sql
create table investments (
  id                bigint generated by default as identity primary key,
  company_id        bigint not null references company(id) on delete cascade,
  name              varchar(150) not null,
  amount_invested   numeric(14,2) not null,
  invested_date     date not null,
  status            varchar(15) not null default 'active' check (status in ('active','exited','written_off')),
  notes             text,
  created_by        bigint not null references users(id),
  created_at        timestamptz not null default now()
);

create table investment_returns (
  id             bigint generated by default as identity primary key,
  investment_id  bigint not null references investments(id) on delete cascade,
  amount         numeric(14,2) not null,
  received_date  date not null,
  notes          text,
  created_at     timestamptz not null default now()
);
```

### Endpoints
```
GET    /api/investments                → { investments: [{ ...investment, total_returns: number }] }
POST   /api/investments
GET    /api/investments/:id            → { ...investment, returns: InvestmentReturn[] }
PUT    /api/investments/:id
DELETE /api/investments/:id
POST   /api/investments/:id/returns    { amount, received_date, notes? }
```
مفيش endpoint ملخص منفصل — الفرونت إند بيحسب الإجمالي المستثمر/العائد/نسبة العائد من نفس قايمة `GET /api/investments` (كل عنصر بيرجع `total_returns` جاهز).

## 5. إضافات على Notifications

أضف للـ `type` check constraint الموجود في جدول `notifications`:
```
'file_uploaded', 'file_status_changed', 'file_comment_added', 'renewal_reminder'
```
(نفس تحذير الأعمدة الناقصة اللي حصل قبل كده مع `feedback`/`project_links`/`credentials` — لو الجدول اتعمل بقايمة قديمة من الـ enum، لازم `ALTER` يضيف القيم الجديدة فعليًا على القاعدة الحقيقية مش بس في ملف الميجريشن).

`renewal_reminder` مقترح لـ Cron job شبيه بـ `meetingReminders` الموجود، يفحص `recurring_revenue`/`recurring_expenses` اللي `next_renewal_date` قريب ويبعت تذكير لصاحب الحساب (`created_by`).
